# m4l integration surface

The Max-for-Live device is the boundary where stemforge's filesystem outputs (manifests + WAVs under `~/stemforge/processed/<track>/`) become Ableton Live state — clips on tracks, tempo on the transport, warp markers on bars. Five JS modules under `v0/src/m4l-js/` carry this load, and they fan out from the manifests on the left to LOM mutations on the right. Two of them — `sf_arrangement_loader.js` and `stemforge_loader.v0.js` — sit on the critical path for "audio plays at the right time"; the other three (clip export, arrangement reader, template duplicator) are around-the-edges plumbing for getting bars back out of Live.

The reason the diagram is split between an `arrangement` lane and a `session` lane is that the two paths have **incompatible warp invariants**. The arrangement loader sets `clip.set("warping", 0)` and writes `start_marker` / `end_marker` / `loop_start` / `loop_end` in **seconds**, because the prechop pipeline emits chunks that are already rendered at the manifest BPM — Ableton's auto-warp guess (which has the same 4/3 bias librosa has on hip-hop) would actively fight the manifest tempo. The session-view path goes the other way: curation v2 places raw stem material that needs warp-aware tempo analysis, so it sets `warping=1`, calls `add_warp_marker` with a `Dict({beat_time, sample_time})` for each anchor, and converts the same marker fields to **beats** via the slope encoded by those warp markers. Set the unit wrong and Live silently clamps clip boundaries to nonsense — `applyCurationV2Clip` has a multiplied-by-`secToBeat` block exactly because we got bitten on this.

When something doesn't load, look in this order. (1) `~/stemforge/logs/sf_debug.log` — every JS module appends here with a `[sf_*]` prefix; this is faster than the Max console because it survives reload. (2) The manifest file the module read — if `bpm` is missing, the loader silently uses `120.0`, and clips drift. (3) The shared dicts (`sf_settings`, `sf_state`) — the device-wide config (paths, current track, preset dir) lives here and is the one piece of cross-module state; if a JS module is reading the wrong manifest dir, this is where the wrong path is. (4) Ableton's track-name heuristics — both loaders fall back from "exact name" to "name contains stem name" to "create new audio track at end"; if your tracks are named oddly, you may end up with appended duplicates instead of clips on the expected tracks. STEM_COLORS in `stemforge/config.py` is the source of truth for the color the JS uses on duplicates — drums red, bass blue, vocals orange, other green.
